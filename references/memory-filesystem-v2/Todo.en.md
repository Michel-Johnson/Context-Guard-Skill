# Todo.md format

## Status

- `Open`: recorded, not started.
- `InProgress`: the Developer and Tester workflow is not complete.
- `Done`: the current requirement has passed acceptance.

Solution attempts use `Confirmed` and `Refuted`. When later requirements or evidence invalidate an earlier solution, update that attempt with `RefutedBy` and the reason.

Migration compatibility: Todo A1 generated by the current runtime may omit `Status`. That legacy projection does not yet conform to this format and does not introduce a third attribution status. Do not synthesize the field or treat its absence as `Confirmed` before the generator is fixed.

## Template

```md
# <Todo ID> <Title>

Reporter: <Human|Agent>
Status: <Open|InProgress|Done>
CurrentAttempt: <A1...An>

## 1. Requirement

<Confirmed user goal>

## 2. Later adjustment events

- <Attempt / Human|Agent>: <New constraint or scope change>

## 3. Acceptance criteria

### A1
<Executable acceptance criteria for this attempt>

## 4. Solution and code changes

### Current valid solution
<Solution conclusions that still hold>

### A1
Status: <Confirmed|Refuted>
RefutedBy: <Attempt, only when Refuted>
Reason: <Reason, only when Refuted>

Solution: <Solution proposed in this attempt>

#### code index
- `<code path>`
  <Change summary>

## 5. Tests

- [A1](tests/<Todo ID>-A1.md): <one-line result>

## 6. Implementation Session index

- [A1](traces/<Todo ID>-A1.md)
```

## Three-attempt example

```md
# T002 Show feedback submission state

Reporter: Human
Status: InProgress
CurrentAttempt: A3

## 1. Requirement

Show an explicit state during feedback submission and prevent duplicate execution.

## 2. Later adjustment events

- A1 / Human: disabling the button removes cancellation; cancellation must remain available.
- A2 / Human: multiple windows still duplicate submissions; scope expands to cross-window consistency.
- A3 / Developer B: use a server request key and define conflicts for different content using the same key.

## 3. Acceptance criteria

### A1
Show progress, prevent a second request, and allow cancellation.

### A2
Two windows submitting the same draft create one record.

### A3
Same key and content return one record; different content returns a conflict; a new request is allowed after cancellation.

## 4. Solution and code changes

### Current valid solution
A client state machine provides progress and cancellation. A server request key and uniqueness constraint provide cross-window idempotency.

### A1
Status: Refuted
RefutedBy: A2
Reason: disabling one button cannot provide cancellation or cross-window consistency.

Solution: disable the button and show loading during submission.

#### code index
- `src/ui/FeedbackForm.tsx`
  Add the submitting state.

### A2
Status: Confirmed

Solution: use a cancellable state machine for one-window submission.

#### code index
- `src/ui/feedbackSubmission.ts`
  Manage idle, submitting, and cancelling states.

### A3
Status: Confirmed

Solution: enforce atomic idempotency by user and request key on the server.

#### code index
- `src/server/createFeedback.ts`
  Validate the request key and handle uniqueness conflicts.
- `src/storage/migrations/004_feedback_unique_key.sql`
  Add the composite uniqueness constraint.

## 5. Tests

- [A1](tests/T002-A1.md): progress passes; cancellation fails.
- [A2](tests/T002-A2.md): one window passes; multiple windows fail.
- [A3](tests/T002-A3.md): state, cancellation, cross-window, and conflict regressions pass.

## 6. Implementation Session index

- [A1](traces/T002-A1.md)
- [A2](traces/T002-A2.md)
- [A3](traces/T002-A3.md)
```
