## 1. 目标与边界

Coordinator 是唯一面向用户交流的 Agent：理解想法、帮助梳理、引出关键意图，结合整个项目定位节点，再组织执行与审核。核心体验是响应快、说人话、操作直观。

- 全局入口知道全部节点及模块的 description；具体记忆按需加载。
- 用户从节点或事项进入时，自动带入该事项及对应链路上下文，不要求重复输入。
- 操作 Map 与触发动效是同一条动作链：调用既有操作接口，由页面呈现结果。
- 节点引用、问题、选项、确认及结果均采用明确的交互结构，不让用户从长文里找操作。
- Coordinator 可新建模块、节点；业务挂载确认与后台接口权限是不同概念，不增加逐节点技术授权步骤。
- 普通讨论不自动变成开发任务；明确执行意图才进入任务流程。

## 3. 上下文设计

### 3.1 全图静态目录

每个对话开始时自动提供全部节点的稳定 ID、父节点 ID、短标题、description（映射现有 purpose 字段）和 Main 版本。不要求模型逐层调用 read_map 才能认识项目。

目录不夹带任务全文、工具日志或所有历史记忆。服务端按项目和 Main 版本缓存，只在地图变更后重建。超大地图按模块组织可展开目录，禁止无提示截断导致节点不可见；具体预算由真实地图测量决定。

### 3.2 挂载链路上下文

从节点进入时立即提供目标节点、祖先链和事项原文。确认挂载后加载该链路的静态记忆、职责与 owns；直接相关节点按需补读，不默认灌入所有兄弟、子孙节点的完整记忆。

每段上下文带来源、版本及更新时间。长记忆分级加载：先摘要和索引，再读取相关原文；摘要保留原文引用。变更节点只刷新受影响的上下文，不让每轮对话重新遍历地图。

### 3.3 会话与执行上下文

会话持续保存：原始目标、已确认内容、待答问题、候选/确认节点、事项类型和引用、近期对话、历史摘要。执行 Session ID、conversationId、taskId 分开存储，避免把用户对话迁移等同于更换执行进程。

任务阶段、Plan、CI 和验收材料按当前阶段读取权威对象，不能把旧对话里的状态当成实时状态。历史摘要不能丢失用户否定、约束或确认范围。

## 4. 工具与接口接线

先建立现有工具—服务端接口—前端动作对照表，核对读写身份、输入、回执及事件；以下是能力清单，不要求新建同名 API。

| 能力 | 复用基础 | 计划 |
| --- | --- | --- |
| 全图目录、链路记忆 | `read_map`、权威 Main 读取 | 提供轻量上下文组装，缺少数据再由工具读取 |
| 定位、展开、聚焦节点 | 现有页面节点导航逻辑 | 核实现有远端动作入口，复用动作和事件链，不另做动画工具 |
| 创建、改名、移动节点 | Main 结构提交与版本/幂等机制 | 接入 Coordinator；服务端确定身份，模型不能声明 human/developer |
| 提问与选择 | `ask_user` | 扩展类型化节点选项；问题带唯一 ID，回答直接关联 |
| 查找与继续会话 | 会话索引、事项对话入口 | 按用户描述检索摘要；有歧义才展示候选按钮 |
| 挂载事项 | 现有事项、对话与挂载确认接口 | 覆盖 TODO/Bug/Idea，原子保存节点、事项和对话关联 |
| 派发与审核 | `prepare_task`、`dispatch_task`、`review_plan` | 保留版本核验，减少重复确认和重复读对象 |
| 测试及产出 | `request_ci`、`read_task`、`read_object` | 按意图整理交付与验收材料 |
| 中断、返工、关闭 | `resume_task`、`request_rework`、`complete_task` | 区分技术恢复与业务返工，复用既有工作流 |

读取工具可并行、同版本结果可复用；有依赖的写操作按顺序执行。未知写入结果先查同一 operationId 回执，不换 ID 盲目重复。

节点删除和合并会涉及事项、子节点与历史引用迁移，不作为创建/改名的附带动作。只有语义明确且接口支持时才展示这些操作按钮。

## 5. 消息与按钮设计

统一消息块：普通文字、节点引用、问题、业务确认、交付结果。优先扩展现有持久消息结构，不重复建设另一套聊天存储。

- 节点引用使用 nodeId；前端显示当前短标题。内部 ID、版本和 owns 不默认混入正文。
- 节点改名后，历史按钮仍指向原节点并显示当前标题；审计记录保留原始内容。
- 同名节点以父级路径辅助区分。失效引用显示明确不可用状态，不链接到名称相近的节点。
- 点击节点按钮定位地图、触发现有动效，保留对话面板、滚动位置及输入草稿。
- 选择题直接显示按钮及补充输入；开放问题有独立回答区。多个问题分别提交，问题归属不得串线。
- 选择/回答与批准执行使用不同语义，答案不会误触发派单。已有明确确认不再多次询问。
- 点击后立即显示提交状态；回执到达后更新结果。失败保留输入并提供重试，避免无反应和重复提交。
- 旧消息按兼容路径显示；停止用短标题子串匹配制造半个按钮。流式期间未完整的引用不能变成可点击操作。
- 超过 60 字按语义分段，保护 URL、代码和节点引用；隐藏装饰分割线和重复角色标签，保留必要错误提示。

## 6. 意图与会话流程

全局自由讨论 → 推荐节点 → 用户确认挂载 → 保存事项及同一对话 → 补足执行目标 → 派发 → 循环审核 Plan → 检查产出 → 辅助用户验收。

流程是可返回和可暂停的：用户改主意时修订意图；挂错节点时重新定位；只聊想法时保存 Idea，不强迫进入派单。用户直接从已有事项进入时，恢复原会话及已确认信息。

每轮只问会影响下一步的关键问题。节点 ID、文件路径等可由工具查到的信息不交给用户补。对“部署博客”始终保留“能访问”的目标，不能因缺少技术参数缩成“只定位源码”。

全局入口检索已有话题后直接继续原 conversation；不要把所有事项历史塞进一个总会话。不同事项拥有独立草稿和提问状态，执行队列阻塞不能阻止用户继续讨论。

## 7. 响应速度

先记录真实基线：请求到达、等待调度、上下文完成、模型首字、工具开始/完成、首个有用内容、最终完成。按自由讨论、节点定位、查询状态、写 Map 分别统计 p50/p95。

改造顺序：版本缓存和少读上下文 → 流式传输与页面增量显示 → 减少模型工具往返 → 用户对话与后台事件公平调度。保留单会话顺序，避免一个慢调用占住整个项目；并发上限由服务能力决定。

普通交流默认一次模型调用；已知静态目录无需再读，独立读取可批量完成。复杂审核仍允许较长处理，但真实显示正在查什么，不用无意义的“收到”算速度达标。

初始目标（待基线验证）：提交后 200ms 内本地反馈；普通短对话首个有用内容 p50 ≤2 秒、p95 ≤5 秒。分别报告模型供应商时间与本系统开销，不能承诺所有工具任务两秒完成。

不在本计划中擅自更换供应商。先核验当前模型及流式协议兼容性，再决定是否有必要调整配置。

## 8. 执行、验收与恢复

Coordinator 审核 Plan 时读取已确认需求、挂载链路和准确 Plan 版本；不通过则给原执行任务具体修改意见，通过才继续执行。

产出审核检查结果是否满足原意图，再给用户可操作的验收材料。材料由任务类型决定：部署提供实际地址及访问验证；界面改动提供入口和操作步骤；源码定位提供候选路径和证据。不能强制所有任务都有 URL，也不能只用 CI passed 代替可验收交付。

“验收不通过”在卡片内展开反馈输入，提交后有明确回执并保留原任务上下文。

需要统一的规则：文章写明产出初审后不自动重启任务；历史要求未完成任务中断后自动继续。建议实现为：技术性异常退出恢复原任务；完成产出后的不满意、目标改变或返工，不因初审意见自行启动新一轮。用户主动暂停/取消不能被自动恢复。CI 失败是否自动返工需在实现前统一到同一规则，不能让旧提示词自行决定。

## 9. 分阶段交付

| 阶段 | 工作与交付物 | 完成标准 |
| --- | --- | --- |
| P0 基线与契约 | 接口对照表、耗时基线、对话样例、上下文/消息字段及工作流规则 | 每项能力明确已有/待接线/缺失；确认恢复与返工语义 |
| P1 上下文 | 全图目录、链路加载、缓存、摘要及版本刷新 | 全局认识所有节点；节点入口无需重复介绍；改图后下一轮读取新上下文 |
| P2 消息和按钮 | 节点 ID 引用、问题和确认卡片、统一提交状态、旧消息兼容 | 无半个按钮；改名仍可定位；原位回答、草稿和面板保留 |
| P3 速度 | 分段流式响应、上下文复用、调度隔离、工具往返优化 | 真实模型基线前后可比较；慢任务不阻塞无关对话 |
| P4 Map 与会话 | 接入 Map 操作、TODO/Bug/Idea 挂载、话题创建与找回 | 用户从讨论到挂载再恢复为同一会话；动作及动效一致，刷新保留 |
| P5 意图到交付 | 意图状态、派发、Plan 审核、产出卡片、验收反馈 | 原目标贯穿任务；验收材料可用；中断恢复与返工行为符合统一规则 |
| P6 灰度与收尾 | Blog 实际场景、兼容迁移、观测、上线及回滚记录 | 端到端证据和性能报告齐全，历史对话和任务可继续 |

阶段可拆成小 PR。P2 与 P3 都依赖 P0 的消息契约；P4 依赖 P1/P2；P5 复用 P4 会话关联。每个阶段交付可直接体验的结果，不等待所有模块做完才展示。

## 10. 验收场景

1. “我想改善阅读体验”：立即结合全图提出具体方向，通过节点按钮定位，问一个关键问题。
2. 从 TODO 输入“增加搜索”进入：原话自动进入会话，不要求再输入一次。
3. “把刚才聊的搜索继续做”：找到原会话并保留已确认条件；同名话题用候选按钮选择。
4. “内容”节点改名：旧消息按钮仍定位正确节点，没有被短名称匹配切碎。
5. 回答多个事项的问题：各自原位提交，刷新后答案仍在，互不串线。
6. 新建二三级节点：调用 Map 操作后页面呈现变化，刷新保持；失败不能假称成功。
7. “把博客部署到服务器”：需求不被改成只读定位，最终验收有真实可用入口。
8. 执行进程中断：恢复原任务；主动暂停不恢复；产出初审意见不会擅自重启执行。
9. 点击验收不通过：输入反馈、提交、显示处理状态，后续依据原任务继续。
10. 网络断开或写入响应丢失：恢复后按原回执核对，无重复节点、事项和派单。
11. 后台任务很慢：用户仍能正常讨论另一话题，等待原因清楚，显示状态有权威依据。

实现阶段使用上述必要行为回归、真实模型样例和安装/线上检查验证，不为纯文案或可逆样式增加无效测试。

## 11. 发布与兼容

历史对话、节点 ID、任务引用原样保留，新增字段可选并带版本。先在 Blog 项目灰度，保留旧渲染兼容；回滚时已保存的新消息仍可读，不以覆盖数据回滚功能。

涉及协议或消息结构时先部署兼容的读取端，再开启新写入。发布前保留数据和配置备份，发布后核对 Cloud、安装入口及前端实际版本。

最终交付：接口对照表、上下文组装器、结构化消息及按钮、流式响应、Map 工具接线、可找回的事项会话、任务与验收闭环，以及真实性能和端到端验收记录。
