# 工程规范：现状与约束

核对日期：2026-09-12。源码基线：`284823a7`（Main）。这是公开源码与流程的审查摘要，不含私有开发记忆；没有连接、挂载或验证生产工作台。历史验收文字不作为当前生产状态证明。

## 阶段一交付

目标：在引入外部规范前，识别已有规则、实际执行入口、权责和缺口。以下“存在”指源码或文档存在，不代表已经运行全部验收。

### 当前流程

```text
需求/业务验收条件（尚缺统一模板）
  -> 确认变更范围、最新 main、平台分支
  -> 设计/Plan（仓库直接开发与 Cloud 角色编排的上下文不同）
  -> 实现与开发者测试
  -> 暂存快照安全检查、产品/测试分支检查
  -> 推送历史安全检查、PR
  -> Required：安全 + 功能/包 + 最低运行时 + 安装 + 浏览器 + 客户端 + 站点
  -> 合并 main
  -> 按变更范围进行安装/运行验收、版本化归档
  -> npm 发布为独立标签工作流，不是合并 main 自动发布
```

### 权责

| 参与方 | 负责 | 不应冒充的证明 |
|---|---|---|
| 用户/产品负责人 | 需求、验收标准、高风险或新增权限批准、业务验收 | 对实现的同意不自动授予生产凭据或浏览器能力 |
| 开发者/开发 Agent | 范围分析、设计、实现、回归、可复现证据 | 自述成功不是独立测试结论 |
| Reviewer/测试角色 | 挑战实现与测试、对准确 SHA 给出判断 | 同一 Agent 自检不宣称独立审核；审批文本不替代协议授权 |
| GitHub CI/CD | 执行已配置检查、形成 SHA/制品关联记录 | 自动检查不证明所有业务场景、原生宿主或生产都通过 |
| Cloud/私有记忆服务 | 持久化、版本保护、授权边界及发布回执 | 同步成功不证明代码合并、任务完成或业务验收 |

## 已核实的缺口与冲突

| ID | 观察及证据 | 风险 | 规范工作中的处理 |
|---|---|---|---|
| B01 | AGENTS 仍说服务器实现/迁移 pending；server-memory 记载已验证实现及一次迁移，CI_todo 也有已部署与未完成专项 | 一句话覆盖所有状态导致错误阻塞或错误完成声明 | AGENTS 只指向版本化状态来源，不静态重复部署结论 |
| B02 | 清单校验递归遍历；runner 只读取固定根目录的直接文件且自行维护排除列表 | 未来嵌套测试可能经过清单校验却未运行 | 明确当前仅顶层自动执行；需证明实际执行集合，新增统一发现能力另立实现任务，不假称已有 |
| B03 | .skip 检查只接受有字符串名称的部分语法，不能证明存在有效跳过理由；.only 检查也只是文本模式 | “通过检查”被当成没有所有形式的聚焦/跳过 | Reviewer 检查原因与范围；工具局限显式记录，不宣称全面 AST 校验 |
| B04 | 已有测试责任、安全、发布规范，但缺少跨阶段的统一输入/输出和验收模板 | 需求、设计、测试、交付之间无法追溯 | 新增精简流程主文与证据模板，引用现有专项而不复制 |
| B05 | 每 PR 现行完整 Required；没有基于风险降低远端门禁的已实现机制 | 文档建议被误读为允许跳过门禁 | 分级只决定设计深度、开发迭代与附加验收；不降低现行 Required 和 npm test 要求 |
| B06 | RULE 对合并后安装与清理 temp 用统一措辞；有只改仓库文档或需保留未完成实验的情况 | 无关全局安装、误删其他工作树/证据 | 提出有范围证据的 N/A 和保留策略，审批前不擅自删除、升级或豁免安全 |
| B07 | npm runbook 写普通分支 push 触发 CI；当前 ci.yml 的 push.branches 只包含 main，PR 到 main 另触发 | 普通分支推送被误报已经有 CI | 流程以当前 workflow 为准，修正说明；任何触发变更单独审阅 |
| B08 | development-security 仍要求在 Python 中登记测试白名单；现有 branch_guard 读取暂存区 manifest | 维护第二份清单并不能改变真实批准集合 | 对齐已有测试治理，文档只引用唯一 manifest，不改工具 |

这些发现是静态证据支持的边界，B02/B03 不代表已经发现当前测试漏执行或恶意代码。阶段六应对关键边界做隔离反例验证，并保留失败证据。

## 不变约束

- 不挂载真实工作台、不读取/复制私有 Session、生产数据或密钥来填充公开规范。
- 不改变人类审批、Agent 能力、服务器权威或完整历史保留策略。
- 不改部署、npm 发布、原生宿主信任或收费模型调用授权。
- 不为了文档整齐迁移源码、替换测试框架或重写角色设计。
- 规范上线仍走 PR 与现有安全/Required；已有尚未完成的产品验收不因规范验收而被关闭。

2. 官方资料精读：按编码/设计/测试/发布/运行分别记录来源、语境、例外及成本。
3. 采纳表：直接采用、调整采用、暂缓、不采用，并处理本页冲突。

5. 规范入口、检查清单及自动化覆盖；未实现检查仍明确标记。
6. 真实历史任务回放与隔离可执行反例，当前规范变更自身走实际交付；不以纸面模板验收代替生产发布。
