# 实验结论

这些结论针对固定源码版本和少量真实GLM样本，尚未成为产品默认策略。质量错误、失败和后半段服务故障必须与耗时一起阅读。

## 执行分身

| 策略 | 原问题平均耗时 | 途中追问平均耗时 |
| --- | ---: | ---: |
| 不分身 | 36.9秒 | 37.4秒 |
| 自适应 | 51.8秒 | 18.7秒 |
| 加强委派提示 | 52.0秒 | 21.6秒 |

分身主要改善调查期间的可对话性，本轮没有证明最终答案更快。fork对象创建平均约2.7毫秒；分派、额外检索、汇总和失败返工才是主要额外时间。加强提示未强制所有任务fork。

## 独立接待

串行组的追问平均34.2秒；独立接待专用规则组约3.6秒。接待规则+人工选择的相关源码预取组，原问题约7.9秒、追问约4.6秒。

两批实验分别进行，第二批根据第一批失误修订规则，缓存与服务波动未完全控制。结果支持继续研究“连续执行+空闲接待快照”，但不证明任意query路由、改向或UI投递已经完成。

## 联网任务

服务持续报错前的三对记录：单产品查询43.9→53.7秒，第二轮54.7→180秒仍未完成，双产品查询31.5→116.7秒。双产品分身中出现STEP_LIMIT并由主会话补查。

随后搜索服务连续返回SEARCH_PROVIDER_ERROR，快速的失败通知不算成功联网答案。因此不能给出三轮有效完成均值，也不能归因于已确认的额度或权限问题；适配器未保留足以区分根因的供应商错误文本。

## Harness 优化

| 任务 | 原版调用/耗时 | 证据工具调用/耗时 | Map预取调用/耗时 |
| --- | --- | --- | --- |
| 文件定位 | 4.5次 / 17.3秒 | 2.5次 / 15.8秒 | 1次 / 7.0秒 |
| 跨模块机制 | 7次 / 32.5秒 | 7次 / 41.6秒 | 5次 / 31.8秒 |

7秒版本仍把storage.rs误说成数据库读写模块，不能上线。增加源码声明后，两次均纠正了该职责，但仍有一次使用过期目录。提示词契约未稳定提升质量或速度。

工具回放的串行搜索等待约9.9秒，并发上限2时约7.3秒，模型调用仍是5次。失败熔断回放可把3次模型往返减到1次，但这是更快报告工具不可用，不是更快交付答案。

## 下一步

1. 工具一次返回有效路径、符号级代码和来源ID，减少猜路径与“先搜位置再读一轮”。
2. 对独立只读调用限并发；保留真实结果依赖，写操作保持顺序。统一取消和日志归属，不能直接用Promise.all替换旧循环。
3. 建立按commit、授权范围和参数绑定的证据池；链接由代码根据来源ID生成，避免模型拼错路径。
4. 优先用当前Map节点和确认的路径定位；词面预取会漏主题，不应加载大量未经核查的旧摘要。
5. 由代码管理参数校验、重复只读查询、搜索熔断和进度状态。失败子任务交回已有证据及未完成点，减少主会话重查。
6. 保留必要多轮，分别测量有意义首字、终稿、成功率和质量。少调用、早报错或少回答都不能自动算提速。
